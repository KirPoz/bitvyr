# Работа с Bitvyr

В репозитории три точки входа ESP-IDF.

- `bitvyr_nes_p4/betta` — редакция P4.
- `bitvyr_nes_p4c6/beta_0_1` — исходники выпуска P4+C6 Betta 0.1 из тега `betta-0.1`.
- `bitvyr_nes_p4c6/beta` — экспериментальная редакция P4+C6 для дальнейших исследований. Версия прошивки `0.1-dev`.

Модули в корневом `cmake` используются всеми тремя проектами. При изменении общих модулей проверяйте сборку выпуска.
P4 вычисляет видео и PCM локально. P4+C6 использует C6 для PCM и Bluetooth,
сохраняя цифровой тайминг NES на P4. Обе редакции используют FAT32 и `/nes_rom`.

## Исходники и сборка

- Ядро `app/nes/core` — собственный переносимый C++17. ESP-IDF, FreeRTOS,
  SDIO, PPA, I2S и heap caps находятся на стороне аппаратных адаптеров.
- Рабочий профиль задаётся в исходниках и `sdkconfig.defaults`. Поддерживайте
  **Full Clean Project → Build Your Project** через ESP-IDF 6.1 для каждой папки проекта. У каждой один
  генерируемый `build`. Нативные тесты размещают свой выход в `build/native` после сборки ESP-IDF либо во временной папке вне дерева.
- Основной профиль P4 использует CPU 400 МГц, Flash 80 МГц и PSRAM 200 МГц.
  `NES_P4_CPU_OVERCLOCK=OFF` выбирает 360 МГц. Изменения частот, памяти,
  разделов, загрузчика и C6 worker проверяйте на фактической ревизии платы.
  Пишите на устройство в пределах выданного разрешения и фиксируйте образ
  и параметры, с которыми проведён замер.
- Зависимости записывайте в manifests и lockfiles. Для изменённого vendor-кода
  сохраняйте provenance, лицензию и связь с точной версией. SDK, managed
  components, toolchain и binaries считаются генерируемыми зависимостями.
- Проверяйте реальные compile commands, link map, ABI, размеры буферов, HP
  memory caps и stack watermarks. PRIVATE параметры могут менять реализации
  внутри единицы трансляции. Layout общего типа должен совпадать у потребителей.
- Удаляйте код после проверки всех потребителей: firmware, native tests,
  callback, inline и template, CMake, linker, генератор и сценарий устройства.
  Сохраняйте ссылки на фактическую проверку. Независимый эталон теста нужен для
  обнаружения ошибок алгоритма и составляет отдельную реализацию.

## Лицензия и публикация

- Корневой `LICENSE` задаёт GNU AGPLv3 для собственного кода, документации и инструментов. У стороннего кода сохраняйте его SPDX, copyright, лицензию и применимые NOTICE.
- Оставляйте проектные настройки VS Code переносимыми. SDK выбирается в расширении, UART указывается для конкретной платы. SDK, архивы игр и прошивки собираются локально.
- Перед публикацией проверьте всё дерево и историю, которую отправляет Git. В журнале сохраняйте SHA, условия и итоговые числа. Личные пути и уникальные идентификаторы устройств заменяйте переносимыми обозначениями.

## Владение ресурсами

- Worker CPU1 владеет изменяемой Machine. Main CPU0 владеет меню, SD, настройками,
  композицией RGB565, PPA/LCD и I2S. Между ними используются пакеты и принятые
  снимки с полным ключом сеанса, ROM, слота, кадра и временной границы.
- В P4+C6 обычные картриджи используют Frame, MMC5 использует Thin/Coupled.
  Для C6 аудиопакет дополнительно связан с транспортной эпохой и номером запроса.
  P4 проверяет совместимость C6 по HELLO/admission. Учитывайте совместную
  нагрузку Bluetooth и SDIO и сохраняйте ограниченные очереди.
- Публикация данных, получение ответа, ACK, освобождение source, завершение
  Worker и фактический join — разные события. При тайм-ауте удерживайте
  ресурсы до подтверждённого завершения. Перед сменой ROM завершайте Worker,
  видео и аудио, снимайте C6-привязку после освобождения источника.
- PPA освобождает источник RGB после чтения. LCD позже освобождает свой
  буфер вывода. Перезапись каждого ресурса разрешена соответствующим событием.
- Внутренняя память P4 включает LP/RTC RAM. Для горячего объекта проверяйте полный
  адресный диапазон HP, capabilities и alignment. Статическая оценка стека
  дополняется минимальным наблюдённым остатком на устройстве.
- Одна активная ROM может находиться в PSRAM. Flash хранит программу и настройки.
  Обновление P4 выполняется app-flash после проверки платы и владельца COM.
  Для аппаратного прогона назначьте одного владельца COM. Перед установкой
  диагностического приложения закрепите обычный образ и его ELF SHA256. После
  прогона проверьте восстановление по журналу загрузки.
  Сохраняйте SD, ROM, сохранения и настройки пользователя. `text.txt` — личная
  заметка, сохраняется в дереве и исключена из коммита.

## Код и документация

- Пакетный README кратко объясняет ответственность, интерфейс, зависимости,
  владельца ресурсов, ошибки и проверку. Комментарии на русском описывают
  назначение методов и нетривиальные условия: единицы, предельные значения,
  время жизни указателя, порядок публикации и причину защитной проверки.
  Идентификаторы протокола, vendor notices и имена SDK сохраняйте как в исходнике.
  Для закреплённых по SHA входов рецепта C6 описывайте назначение на русском
  в README пакета. Перед изменением этих входов проверяйте рецепт через
  команду аудита из руководства C6.
- В `docs` каждой редакции пять документов: проект, архитектура, руководство,
  результаты, открытые задачи. Mermaid описывает путь кадра и критический путь.
  Актуальная документация описывает поддерживаемую конфигурацию и результаты
  измерений с их условиями. Выводы по каждому диагностическому образу
  сохраняйте в журнале с собственным SHA, областью проверки и решением.
- Текущие записи хранит корневой `experiments.json`, прежние записи и
  доказательства находятся в `experiments/`. Добавляйте события через
  `python tools/experiments.py --event FILE`. Запишите цель, отличие от базы,
  версию и SHA исходника/образа, параметры, сцену, числа, ошибки и решение.
  Успешные, отрицательные и прерванные попытки сохраняйте как события. Перед
  Full Clean переносите итоговые замеры и выводы диагностики с SHA исходных
  отчётов. Проверьте, что они доступны из чистого Git через `--id`, а для
  перенесённого отчёта также `--sha`. Ввод сохраняйте в закреплённом банке
  сцен с CRC ROM, временем кадра и доказательством фазы игры. Бинарные сборки, ROM, сырые трассы,
  снимки, одноразовые патчи и тестовые копии храните в генерируемом `build`.
- Для нового измерителя фаз подтвердите закрытие окон и запись отчёта на
  коротком аппаратном маршруте. Тяжёлую сцену оценивайте отдельным замером.
- FPS сравнивайте на одинаковых ROM/CRC, вводе, регионе, сцене и звуке.
  Считайте produced, accepted и submitted отдельно. Используйте отметки времени
  платы и указывайте длину окна. CPU0, CPU1, C6 и DMA перекрываются. FPS по
  программной обработке и физическая развёртка — разные измерения.
- Для каталога закрепляйте по три окна в 120 гостевых кадров. Указывайте
  доказательство сцены, полноту наблюдаемого ввода и границы ROI.
  Цель 59,5–60,5 FPS подтверждается при непрерывном покрытии всех окон
  сцены и согласованных счётчиках кадра.
- Проверяйте корректность CPU/RAM, IRQ, MMIO, PPU и аудиотайминга на границах.
  Отмечайте отдельно нативные тесты, сборку, flash, загрузку, аппаратный прогон
  и качество LCD, звука и Xbox. Не повышайте статус результата при повторном
  анализе старых данных. В Git включайте исходники, тесты, документацию,
  журнал и настройки проекта. Секреты, ROM, игровые ресурсы и временные артефакты исключайте.
- Перед коммитом проверьте чистую сборку обеих папок через настройки
  ESP-IDF, зависимости по карте линковки, нативные тесты и ссылки. Для
  проверки из терминала воспроизведите CMake/Ninja-вызовы расширения и
  зафиксируйте, как проверялась сборка. Сверьте SHA-256 `text.txt` до и после очистки.
- Публикуйте проверенный коммит в `main` обычным push. Проверьте, что GitHub
  возвращает тот же SHA. Теги замороженных опытов остаются локальными.
